# Мониторинг задержек вылетов аэропорта Стригино (GOJ)

Читает онлайн-табло вылетов <https://ar-goj.ru/board/?ready=yes>, фиксирует
задержки в SQLite и присылает оповещения в Telegram.

Работает на стандартной библиотеке Python — ни pip, ни venv не нужны. Это
осознанное решение: на роутере с OpenWrt каждый мегабайт флеш-памяти на счету.

Требуется Python 3.7 или новее.

## Быстрый старт

```sh
cp config.example.json config.json     # впишите telegram_token от @BotFather
python3 -m strigino board              # посмотреть табло, ничего не записывая
python3 -m strigino run                # запустить мониторинг и бота
```

Затем напишите боту `/start` в Telegram — чат подпишется на оповещения.

## Установка

**Debian / Ubuntu (systemd):**

```sh
sudo ./install/debian/install.sh
```

**Роутер с OpenWrt (проверялось на 25.12.3, поддерживаются apk и opkg):**

```sh
./install/openwrt/install.sh --data-dir /mnt/sda1/strigino
```

`--data-dir` на USB-накопителе желателен: база пишется при каждом опросе, а
внутренняя флеш-память роутера рассчитана на ограниченное число перезаписей.
Без USB сгодится и значение по умолчанию `/srv`, но период опроса тогда
разумно держать в районе 10–15 минут.

Оба установщика перед установкой проверяют наличие нужных модулей Python и
доступность табло, а токен спрашивают интерактивно (или принимают `--token`).

## Управление из Telegram

| Сообщение боту | Что делает |
| --- | --- |
| число от 2 до 30 | период проверки табло в минутах |
| `/start` | подписать чат на оповещения |
| `/status` | период, порог, время последнего опроса, размер базы |
| `/flights` | ближайшие вылеты и текущие задержки |
| `/threshold N` | минимальная задержка для оповещения, минут |
| `/stop` | отписаться |

Новый период применяется к следующему циклу — ждать текущего не нужно.

## Оповещения

Сообщения размечены HTML-разметкой Telegram. Дата у времени печатается
только когда отличается от даты вылета по расписанию — иначе «9 сентября»
повторялось бы в одном сообщении по четыре раза.

**Первая задержка:**

> ⚠️ **Задержан рейс ZF-443**
> Нижний Новгород → Анталья · `GOJ-AYT`
>
> По расписанию: **9 сентября 20:50**
> Новое время: **22:05**
> Задержка: **1 ч 15 мин**
>
> *Обнаружено 21:02*

**Повторная задержка** — нумеруется и показывает историю:

> ⚠️ **Задержан рейс ZF-443** · задержка №3
> Нижний Новгород → Анталья · `GOJ-AYT`
>
> По расписанию: **9 сентября 20:50**
> Новое время: **23:00**
> Задержка: **2 ч 10 мин**
>
> Объявляли ранее:
> • 22:05 — обнаружено 21:02
> • 22:40 — обнаружено 21:27
>
> *Обнаружено 21:57*

**Вылет задержанного рейса:**

> 🛫 **Вылетел рейс ZF-443**
> Нижний Новгород → Анталья · `GOJ-AYT`
>
> Фактический вылет: **10 сентября 00:10**
> Итоговая задержка: **3 ч 20 мин**
>
> История:
> • по расписанию — 20:50
> • 22:05 — обнаружено 21:02
> • 23:00 — обнаружено 21:57

**Список `/flights`** группируется по дням, пункт отправления в строках не
повторяется — он у всех один:

> 📋 **Ближайшие вылеты**
>
> **9 сентября**
> 10:50 · WZ-1339 → Тбилиси
> 14:55 · FV-6644 → Сочи  ⚠️ **15:30** (+35 мин)
> 17:15 · N4-440 → Сочи  ⚠️ **10 сентября 00:40** (+7 ч 25 мин)

Две настройки на случай, если что-то лишнее:

* `include_flight_number` — номер рейса в заголовке. Нужен потому, что в один
  день бывает несколько рейсов по одному направлению: в Анталью летают и
  U6-1579, и SU-800, и ZF-443;
* `show_total_delay` — строка с суммарной задержкой.

## Как устроено табло

Страница отдаётся сервером уже отрендеренной (Bitrix, без подгрузки данных
скриптами), поэтому достаточно обычного HTTP-запроса. Строка рейса —
ссылка `<a class="table-flex__row">` с семью колонками:

| Колонка | Содержимое |
| --- | --- |
| type1 | время по расписанию (`00:30` + `08.09`) |
| type2 | номер рейса (`FV-5979`) |
| type3 | авиакомпания |
| type4 | направление (`Хургада` + `HRG`) |
| type5 | статус (`Вылетел`, `Посадка`, пусто у будущих рейсов) |
| type6 | ожидаемое / фактическое время |
| type7 | примечание (`Совмещен c N4-829`) |

Дата есть в обеих колонках времени, поэтому задержки через полночь считаются
точно: вылет 7 сентября в 22:15 с фактическим временем 8 сентября 02:24 — это
4 часа 9 минут, а не отрицательная величина.

**Задержка определяется сравнением колонок 6 и 1, а не текстом статуса.**
У будущего рейса без задержки эти времена совпадают. Набор статусов на сайте
меняется, и завязываться на конкретные слова ненадёжно.

Параметр `?ready=yes` оставляет на табло уже вылетевшие рейсы. Без него вылет
выглядел бы как исчезновение строки, и событие «вылетел с задержкой» поймать
было бы нельзя.

Три особенности разметки, которые парсер учитывает:

* **Codeshare.** Один самолёт выводится двумя строками с одним идентификатором
  и одним направлением, но разными номерами (EO-829 и N4-829 в Уфу). Строки
  схлопываются в один рейс, чтобы не приходило два одинаковых оповещения.
* **Рейс с посадкой.** Один идентификатор, но разные направления — это разные
  плечи, они остаются отдельными записями. Ключ рейса поэтому составной:
  идентификатор + IATA.
* **Вылет раньше расписания.** Бывает (Екатеринбург, −12 минут); задержкой
  считается только положительная разница.

## Про антибот

Перед сайтом стоит DDoS-Guard, но при обычном браузерном `User-Agent` он
пропускает запросы: 12 запросов подряд без пауз — все 200, примерно 0,4 с
каждый, без капчи, JS-челленджа и следов рейт-лимита. Cookies не нужны.

При периоде 2–30 минут получается 2–4 запроса за цикл (сегодня + завтра, с
повторами при сбоях) — это ничтожная нагрузка, и проблем ожидать не стоит.
На случай изменений: `user_agent` вынесен в конфиг, сетевые сбои не роняют
процесс (сработает повтор на следующем цикле), а состояние рейсов и факт
отправки оповещений хранятся раздельно, так что при недоступности сайта или
Telegram ничего не теряется и не дублируется.

Если DDoS-Guard когда-нибудь включит JS-челлендж, признак будет однозначным:
`board` начнёт возвращать ноль рейсов при успешном HTTP-коде.

## База данных

SQLite, четыре рабочие таблицы:

* `flights` — последнее известное состояние каждого рейса;
* `delays` — история объявленных времён вылета, по строке на задержку;
* `messages` — очередь исходящих сообщений (переживает перезапуск и
  недоступность Telegram);
* `chats`, `settings` — подписчики и настройки, меняемые из бота.

Раз в сутки записи старше `keep_days` (по умолчанию 14) удаляются; задержки
уходят каскадом вместе с рейсом.

## Логика оповещений

Задержкой считается изменение ожидаемого времени у рейса, который **ещё не
вылетел**. У вылетевшего рейса та же колонка означает фактическое время
отправления, и расхождение в 3–5 минут есть почти у каждого рейса — это не
объявленная задержка, а обычная работа аэропорта. Такие рейсы обрабатываются
отдельно: сообщение о вылете уходит, если задержку объявляли заранее либо
фактическое отклонение превысило `departed_min_delay_minutes` (15 минут).

При самом первом запуске база наполняется молча: иначе пришло бы оповещение
по каждому рейсу, который уже задержан на момент установки.

## Командная строка

```sh
python3 -m strigino run             # постоянная работа: опрос + бот
python3 -m strigino poll            # один цикл (для cron)
python3 -m strigino board           # показать табло, не трогая базу
python3 -m strigino status          # состояние базы и настроек
python3 -m strigino cleanup         # удалить записи старше keep_days
python3 -m strigino test-telegram   # проверить токен и отправить тест
```

Любой параметр конфига переопределяется переменной окружения с префиксом
`STRIGINO_`, например `STRIGINO_TELEGRAM_TOKEN` или `STRIGINO_LOG_LEVEL`.

## Тесты

```sh
python3 -m unittest discover -s tests
```

Разбор проверяется на реальных страницах табло из `tests/fixtures`, а логика
оповещений — на сценарии с серией задержек и вылетом, где тексты сообщений
сверяются дословно.
